## Findings and technical notes

**LCA filing volume does not predict ATS type (2026-09-29).** Step 3 originally planned to seed `companies.yaml` by probing Greenhouse/Lever/Ashby slug guesses for the top LCA filers by volume. Live testing killed this: the heaviest H-1B filers (Amazon, Google, Microsoft, JPMorgan, Citibank) run Workday or proprietary systems, not the three ATS this pipeline can query. A 40-candidate sample of the top of the ranking returned exactly one "hit," and that hit was a false positive, LinkedIn's Greenhouse board is an internal sandbox with job titles like `123123` and `Bug Bash Job`. A sample from the middle of the 2,103-candidate ranking (offset 700) returned a real ~10% hit rate (Peloton, Vanta). Projected full-run cost was several hours of live probing for a small, low-quality yield. Replaced with three targeted discovery sources instead of one blind prober: a curated manual list of the top NY/NJ employers by filing volume (Step 3B), an HN "Who is hiring" scraper (Step 3C, `scripts/seed_from_hn.py`), and JobSpy result auto-discovery (Step 6, source G). Full writeup and the revised Step 3 spec are in `BUILD_PLAN.md`.

**Decision #1 above and Step 3B's exclusion of offshore IT consultancies are answering different questions.** Decision #1 is about which employers' job postings are acceptable to keep once found (through any source) — large consulting/product companies including offshore-delivery firms stay in. Step 3B is about which employers are worth manually curating a direct-ATS-scrape entry for — offshore IT consultancies (Cognizant, TCS, Infosys, Wipro, HCL, LTIMindtree, etc.) rarely post real DS/ML roles on their own public boards (they staff client sites), so they're excluded from that curated list specifically, not from the pipeline generally. If one of their postings surfaces via JobSpy or HN, it's still eligible.

**Manual-browsing-only job sites (2026-09-29).** Built In, Wellfound and YC's Work at a Startup are not scraped. Built In's postings are covered indirectly since Google Jobs aggregates them; Wellfound and YC Work at a Startup have no reliable public API and are left for Sanket to browse by hand.

**Step 3B results (2026-09-30).** Researched the top 50 NY/NJ employers by LCA filing volume by hand: kept Capgemini and Accenture (consistent with keeping EY/Deloitte/PwC per decision #1), dropped University of Rochester (not NYC area), expanded the list from 40 to 50 so the 13 academic/medical entries wouldn't crowd out corporates, and resolved "MPG Operations LLC" to its real brand, Millennium Management (a NYC multi-strategy hedge fund, confirmed via web search to hire Data Scientists and quant researchers). 20 of the 50 resolved to a real, live-verified board on one of our 4 ATS (Barclays, Morgan Stanley, Citigroup, Bank of America, American Express, Accenture, Regeneron, BlackRock, PwC, Bristol-Myers Squibb, Walmart, Fiserv, Deutsche Bank, RBC Capital Markets, Palantir, DoorDash, plus 4 cap-exempt academic/medical: Memorial Sloan Kettering, Montefiore, NYU Grossman School of Medicine, Cornell). The other 30, mostly megacap tech/finance running proprietary career sites (Amazon, Google, Meta, Microsoft, JPMorgan, Goldman Sachs, Citadel, Two Sigma, McKinsey, BCG, etc.) plus several universities/hospitals running non-Workday systems, are listed in `data/private/unresolved_companies.txt` with the proprietary system name where identified. Millennium Management's one real Workday board exists but returned 0 open jobs on live verification, below the 3-job bar; kept in the unresolved file for a later recheck rather than dropped, since the employer itself clearly qualifies.

**`cap_exempt` and the `jobs` table schema (2026-09-30).** Sanket asked to carry a `cap_exempt: true` flag (statutory H-1B cap exemption: universities, their affiliated nonprofits, nonprofit/government research orgs) from `companies.yaml` into the `jobs` table, but only if it fits the existing schema without a new migration. It doesn't: `001_init.sql` has no column suited to a per-company boolean or tag (`red_flags` is specifically for negative JD-derived flags, not a positive company attribute). **No migration was added.** `cap_exempt: true` is set on the 4 resolved academic/medical `companies.yaml` entries (Memorial Sloan Kettering, Montefiore, NYU Grossman, Cornell) and stays there for now. Carrying it forward needs a Step 9 migration (e.g. a `cap_exempt boolean` column on `jobs`, populated at fetch time from the company config, surfaced in the digest as a tag) — ask Sanket before adding it.

**Title regex coverage gap found during Step 4 live testing (2026-09-30).** Running the fetchers against real companies surfaced a real gap in `search.yaml`'s `titles.include` patterns, not a fetcher bug: AI-native companies increasingly use titles like "Applied Research Scientist," "Research Engineer, Data Foundations," or "Research Science Manager, Foundation Models" that are clearly DS/ML/AI-relevant but don't match the current patterns. The `research (engineer|scientist).*\b(ml|ai|machine learning)\b` pattern requires "ml"/"ai"/"machine learning" to appear later in the same title, which plain "Research Engineer" or "Research Scientist" titles never do; `applied (ai|ml|scientist|science)` requires "applied" to be immediately followed by one of those words, which "Applied Research Scientist" isn't. Confirmed directly against Runway ML's live board: 43 open roles, several clearly ML-relevant (the titles above), 0 matched. This is a config-tuning call for Sanket, not something to change unilaterally — flagging here rather than editing `search.yaml`'s title patterns without his input.

**Step 8 API findings (2026-10-01).** Verified live against Haiku 4.5 with `anthropic` 1.9.0. (1) Native structured outputs work (`output_config={"format": {"type": "json_schema", "schema": ...}}`), so the forced-tool fallback is not needed. (2) The API rejects `minimum`/`maximum` on integer fields with a 400, so `rubric.api_schema()` strips them and moves each range into the field description; `ScoreResult` still enforces the ranges and recomputes `total`. (3) `temperature` is not an argument in this SDK version, so the spec's `temperature 0` is not applied. (4) One line was added to the spec's system prompt after a live call showed `red_flags` speculating about the candidate's visa status; red flags are now limited to concerns from the posting itself and never mention immigration status.

**Sanket's rule changes after the Step 8 spot check (2026-10-01).** (1) `min_similarity` set to 0.50. (2) Fit scoring made stingier: the rubric prompt now states the candidate has about 4 years of experience and gives calibration caps (85+ is rare; 5 years required caps `experience_fit` at 10, 6+ at 4; senior or staff scope caps `seniority_fit`; non-NYC/NJ on-site or unclear location caps `location_fit` at 3). (3) US only, and ambiguous location is skipped: `parse_location` no longer treats an empty location as US, `unclear_remote_policy` is now `skip`, and the Workday fetcher falls back to the detail payload's location and country when the list payload has none (this was the Accenture/Pune bug). (4) Skip 6+ years: `max_yoe_required` is now 5, with the exclusion test `years_required_min > 5`. (5) Only jobs guaranteed to be recent: new hard cap `max_posting_age_days: 14`, a new `14d` window, a known `posted_at` is now required from every source (JobSpy included), and rows older than 14 days are expired before scoring. Caveat: Workday only gives day-level relative dates ("Posted 3 Days Ago"), and a reposted requisition can show a fresh date. (6) Ranking is by recency, newest first; implemented in Step 9.

**Fit score formula (2026-10-01).** `fit_score` = skills_match (0-40) + experience_fit (0-20) + domain_fit (0-15) + location_fit (0-10), all judged by Haiku (max 85), plus recency (0-15) computed in code from `posted_at`: 15 points for a job posted just now, falling linearly to 0 at the 14-day cap (`scoring.recency_max_points`). `seniority_fit` was dropped at Sanket's request because years required already drives experience_fit. Recency is fixed at scoring time, so it can be a point or two stale by digest time; the digest sorts by `posted_at` directly.

**Hard YOE filter before scoring (2026-10-01).** `prefilter.min_years_required()` pulls the years-of-experience figures out of the description (patterns like "6+ years of experience", "8-10 years", "minimum of 7 years"), ignores sentences marked preferred, bonus or nice to have, and takes the smallest figure, since a posting asking for "3+ years Python" and "7+ years in the industry" really requires 3. If that figure is above `scoring.max_yoe_required` (5, so 6+ is out) the job is excluded as `yoe_too_high` before embedding or Haiku, so it costs nothing and never gets a fit score. Haiku's own `years_required_min` check after scoring stays as a backstop for postings the regex misses. Checked read-only against 24 stored descriptions; it matched Haiku wherever both had a figure and missed one (BMS, 5).

**Core fit and digest bar (2026-10-01).** `fit_score` in the `jobs` table now stores core fit only (skills_match + experience_fit + domain_fit + location_fit, max 85), so no migration was needed. Recency (0-15) is computed live in the digest from `posted_at`, which also removes the stale-recency caveat above. The digest includes only jobs with core fit at or above `digest.min_core_fit` (50).

**Ranking is recency (2026-10-01).** `rank_score` = whole days since 2026-01-01 of `posted_at` plus core_fit / 1000, so the newest posting day comes first and core fit only orders jobs posted the same day. The old NYC, remote, sponsorship, LCA and freshness bonus weights are retired; `search.yaml > ranking` now holds only `tiebreak_divisor`. Groups are NYC metro, Remote US, Elsewhere US. The `v_daily_digest` view was not changed (it already orders by `is_nyc_metro desc, rank_score desc`).

**Remote with no country (2026-10-01).** `parse_location(raw, cfg, description)` keeps a remote job only when the description has a clear US signal ("United States", "US-based", "U.S.", a US state name, "City, ST", or a USD salary range) and contains no non-US keyword. Also fixed two latent bugs found in the same code: non-US keywords were matched as substrings ("Indianapolis" contains "india") and state abbreviations were matched after upper-casing the text (so the word "in" read as IN).

**Duplicate ATS ids and stale LCA fields (2026-10-01).** Adding the country to Workday locations changed canonical ids for jobs already stored, which tripped the unique `(source, ats_job_id)` index and failed run 6. `upsert_job` now treats an existing ATS id as already seen, and fills any NULL LCA fields on it when the employer now matches (this fixed Walmart rows stored before its alias existed).

**Distance-based location (2026-10-01).** Sanket asked for DC, Philadelphia and nearby areas, scored by real distance. Chosen: the "nearest hub" rule and a separate corridor digest group. (1) `pipeline/geo.py` resolves job location text to coordinates offline with `geonamescache` (GeoNames, US cities of 15,000+ people, no web calls, no cost; pinned 3.0.2) and measures straight-line great-circle miles, not driving distance. (2) `location_fit` is no longer judged by Haiku; code computes it: remote scores 10, otherwise 10 points within 25 miles of the nearer of NYC and Washington D.C., falling linearly to 0 at 250 miles, and an unresolvable location scores 0 (Philadelphia 8, Baltimore 10, Boston 3, Atlanta 0). Core fit is now Haiku's skills + experience + domain (max 75) plus location (max 10), still max 85. (3) Digest groups are NYC metro (within 50 miles of NYC), DC / Philadelphia corridor (within 50 miles of D.C. or Philadelphia), Remote US, Elsewhere US; distance decides when the place resolves and the stored `is_nyc_metro` flag is only the fallback. (4) `is_nyc_metro` at fetch time now also uses distance when the place resolves, fixing "Rochester, New York" and "Newark, DE" false positives. Settings are in `search.yaml > geo`. Limits: a place under 15,000 people, or text with no recognizable city, does not resolve. Not chosen: the "balanced" rule (farther of the two distances), which would have demoted NYC itself.

**Skills score is computed from lists (2026-10-01).** Haiku no longer returns `skills_match`. It returns `required_skills` (at most 12, required not preferred) and `matched_skills` (the subset the resume clearly shows); code computes `skills_match = round(40 * matched / max(required, 1))`, rejects a response where matched is not a subset of required (retried once, then left shortlisted), and caps `experience_fit` at 10 when `yoe_min >= 5`. First evaluation on 13 jobs (read-only, nothing written): core fit min 32, median 64, max 85 versus min 30, median 64, max 74 before. It did not make scoring stricter because Haiku says it matches every required skill on about half the postings. Candidate fix, not built: only count a matched skill if its name appears in the resume text (a deterministic check, no schema change). `digest.min_core_fit` is still 50, pending Sanket.

**cap_exempt (2026-10-01).** Migration `002_cap_exempt.sql` adds `jobs.cap_exempt boolean not null default false` and appends it to `v_daily_digest`. `run.py` syncs it from `companies.yaml` on every run (`sync_cap_exempt`), so it backfills old rows and follows list changes. The digest shows a "[Cap-exempt]" tag. No stored job was at a cap-exempt employer when it was added.

**Step 11 verification (2026-10-01).** `on.schedule` accepts `timezone: "America/New_York"` next to `cron` (GitHub workflow syntax reference; a 2:30 AM schedule skipped by DST advances to 3:00 AM). Latest action majors found with `git ls-remote --tags`: checkout v7, setup-python v7, cache v6. The test suite passes from a clean `git archive` with no `.env` and no `data/`; the tests workflow sets a dummy `DATABASE_URL` because `settings.py` requires one to exist.
